$ evnx init --help
Interactive project setup — generates .env.example.

Three modes available: • Blank: Create empty .env files (add variables later with `evnx add`) • Blueprint: Use a pre-configured stack like "T3 Turbo" or "Rust High-Perf" • Architect: Build your stack step-by-step (language → framework → services → infra)

Usage: evnx init [OPTIONS]

Options:
      --path <PATH>
          Output path for .env files
          
          [default: .]

  -y, --yes
          Skip all prompts. Creates blank .env files unless --blueprint names a stack

      --blueprint <ID>
          Generate from a named stack blueprint, e.g. `t3_modern`.
          
          Selects Blueprint mode without prompting. An unknown id is an error that lists the valid ones, so this doubles as the way to see them.
          
          A blueprint is a shorthand for a component list — `t3_modern` is `--with nextjs,postgresql,clerk,aws_s3,stripe,github_actions,vercel`.

      --with <LIST>...
          Name the components directly, e.g. `--with nextjs,postgresql,stripe`.
          
          Ten fixed blueprints cannot span the stacks people have — "Django + Kafka + Clerk" needed someone to add a `django_kafka_clerk` stack before it could be expressed. This names the pieces instead.
          
          Repeatable and comma-separated: `--with a,b --with c` is the same as `--with a,b,c`. An unknown name is an error that suggests near matches; `--list-components` prints them all.

      --list-components
          Print every component `--with` accepts, and exit

      --detect
          Accept what the project declares, without asking.
          
          Run interactively with no flags, `init` reads `package.json`, `docker-compose.yml` and friends and proposes what it finds. This is how a script says yes to that proposal.
          
          ⚠️ Detection is a heuristic — a `stripe` dependency in a test fixture looks exactly like one in a checkout flow. Prefer `--with` where the answer is known; this is for bootstrapping a project you trust.

      --from-source
          Build the template from the variables the code actually reads.
          
          Scans the project's source and compares it to `.env.example`, so it finds both what is missing and what is declared but named nowhere — the second being something no other evnx command can tell you, since they all treat `.env.example` as the definition of "required".
          
          ⚠️ A heuristic. Variables consumed entirely inside a library, and dynamic access like `process.env[key]`, are invisible in principle.

      --force
          Overwrite an existing .env.example.
          
          `.env.example` is normally a tracked, hand-maintained file, so init asks before replacing it and refuses outright under --yes. This is how a script says it meant to replace it. `.env` is never overwritten.

  -v, --verbose
          Enable verbose output

  -q, --quiet
          Suppress non-essential output

      --no-color
          Disable colored output

  -h, --help
          Print help (see a summary with '-h')

  -V, --version
          Print version

Full guide: https://www.evnx.dev/guides/commands/init
